# Beyond implementation outcomes

## Flexible intake and project profile
- [x] Accept a free-text problem statement alone; optionally accept project description and a validated public GitHub repository URL; optionally disclose project name/category, target users, existing/planned features, languages, frontend/backend technologies, database, AI/ML, architecture, constraints, and desired improvements. No optional detail is mandatory. Progressive disclosure keeps extra details collapsed initially. Offer “Analyze My Idea” and “Analyze GitHub Repository” into one analysis pipeline. When both idea and repo are supplied, reconcile both. Reject empty submission with a helpful inline message; invalid repository URLs trigger no external request and users may continue with a problem statement. **Evidence:** tested problem-only, repository-only, mixed idea+repo, and invalid-URL behavior; invalid URL recovery directs the user to continue without that URL.
- [x] Build and validate a structured project profile with name, underlying problem, solution, target users, core/planned features, technologies, architecture, potential differentiators, constraints, and unknowns. Label sources USER-PROVIDED, REPOSITORY-OBSERVED, or AI-INFERRED. Missing information remains unknown; inferred fields can be edited. Do not force a long questionnaire. Profile preview can be reviewed before/during analysis. **Evidence:** profile is streamed with source pills before GitHub/web discovery; the results dossier displays all profile dimensions; the editor re-sends changed fields only, preserving untouched provenance.

## Evidence-aware research and comparison
- [x] Implement separate modular GitHub REST and Tavily provider adapters with normalized common results. Generate multiple focused queries across problem, functionality, terminology, use case, technical approach, and feature combinations. GitHub may retrieve repo metadata, README, topics/languages, license, tree, dependency manifests, selected source/tests, and activity only as needed; never execute code or download whole repos unnecessarily. Tavily may find products, sites, docs, alternatives, adjacent problem spaces, comparable features and technical approaches. Preserve real source URLs and metadata; do not invent results. **Scope note:** this MVP selectively inspects repository metadata and a capped README excerpt; source-tree/tests are not crawled unless added later.
- [x] Pipeline validates input; builds profile; generates queries; searches available providers; normalizes/deduplicates/filters; ranks; selectively inspects strongest candidates; extracts evidence; compares capabilities; proposes innovation directions; returns structured results. Bound requests and research budget, cache repeated repo lookups where practical, handle timeouts/rate limits/provider failures, and continue with remaining available sources while disclosing reduced coverage. Ranking uses provisional transparent signals: problem similarity 35%, feature overlap 35%, target-user similarity 15%, technical approach similarity 15%; exclude unevaluable dimensions and renormalize. Idea-only analysis emphasizes conceptual/proposed feature overlap; repository analysis also uses observed implementation evidence. Semantic interpretation where practical; lexical fallback. Embedding similarity alone is not proof. Explain each shortlist candidate and avoid duplicates/weak matches. **Evidence:** five-minute/100-entry in-memory GitHub response cache, 512-KiB provider-response cap, timeouts, per-request query/candidate bounds, and a four-analysis concurrency cap; failed sources are named in coverage notes.
- [~] Each comparable project includes actual clickable source, description, relevance explanation, shared/distinct features, technical similarities only when observed, available repo health indicators, supporting evidence, and evidence limitations. Link directly to relevant README/code/docs where available. Distinguish Verified, Inferred, and Unknown; absence of documentation is not proof of absence; documented feature is not proof of complete functionality. Show research timestamp and actual candidates inspected; never claim exhaustive coverage. **Current boundary:** records are based on GitHub metadata/README or Tavily result metadata/snippets; this MVP does not crawl full pages, inspect source trees, or claim end-to-end feature verification. AI-distinctive observations are labeled as inference and shared terms are tied to deterministic source text.
- [~] Compare problem/audience, use cases, features/workflows, technologies/architecture/integrations, repo documentation/tests/organization/activity/license, and UX/onboarding/accessibility only when evidence supports them. Never manufacture unavailable scores. Keep factual observations separate from subjective assessments; do not conflate stars, forks, activity, documentation, or innovation. **Current boundary:** displayed comparisons use available profile, repository metadata/README, and search excerpts; tests, onboarding, accessibility, and full UX are not assessed without direct evidence.
- [x] Feature comparison matrix uses explicit statuses such as Evidence found, Partial evidence, Not established, and Proposed by user; missing evidence is not confirmed absence. Show research source coverage, actual discovered/inspected counts, timestamp and limitations. Any similarity value is labeled heuristic and explains criteria. Show at least two meaningful visualizations if feasible, based only on actual available assessments/data and legible on mobile; explain radar dimensions and only show a collision map when reliable comparison data exists. **Evidence:** source-term matrix, heuristic similarity bars, and a four-dimension radar shown only when all plotted dimensions are available; unsupported radar values are withheld.

## Innovation and repository analysis

Each includes concise title, proposal, addressed problem, differentiation rationale, relevant comparison evidence, expected benefit, low/medium/high effort, practical validation experiment, and remaining uncertainty. Rank by relevance, user value, feasibility, and differentiation potential and explain criteria. Do not guarantee novelty/success, suggest generic “add AI”/“improve UI”, or conflate hypotheses with evidence-backed findings. **Evidence:** all directions are labeled as hypotheses; source references link to returned candidates or explicitly say when no comparison source supports the direction; fallback directions are tailored to profile fields.
- [x] Let users select a direction and generate a refined project proposal (revised concept, problem statement, target users, core features, differentiating feature, technical implementation outline, estimated complexity, validation plan) that builds on the original idea rather than replacing it with an unrelated one.
- [~] For supplied GitHub repositories, optional selective Repository DNA compares stated capability claims with evidence in inspected files, names inspected files and unverified elements, never executes code, and never concludes complete functionality from file presence alone. **Deferred:** the current MVP inspects public metadata and README only; it makes no code-file or full-functionality claims.
